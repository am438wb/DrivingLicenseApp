1. Architecture overview

The solution is a modular layered architecture with a domain-centric state machine and asynchronous processing. It keeps the exercise understandable while implementing the important distributed-system guarantees.

Blazor WebRadzen UI submits and tracks applications.
ASP.NET Core APIHTTP contract, queries, submissions, manual review.
PostgreSQLApplication, audit, outbox, inbox/deduplication.
RabbitMQDurable asynchronous message transport.
WorkerValidation, photo simulation, risk and state transitions.
Architectural choice: a custom state machine was selected instead of Temporal, Elsa, or a MassTransit Saga because the workflow is short, linear, and has no timers, parallel branches, or compensation. This minimizes accidental complexity while leaving upgrade paths clear.

2. Layers and responsibilities

DrivingLicence.Domain

Contains the application aggregate, statuses, legal-transition map, audit-entry creation, business checks, workflow options, and ApplicationSubmitted contract. It has no ASP.NET, EF Core, RabbitMQ, or UI dependency.

DrivingLicence.Infrastructure

Defines AppDbContext, entity mappings, PostgreSQL migrations, optimistic concurrency through xmin, outbox rows, processed-message markers, and safe startup migration/legacy adoption.

DrivingLicence.Api

Accepts multipart submissions, persists application + initial audit + outbox atomically, exposes status/history, validates reviewer credentials, and performs guarded manual approval or rejection.

DrivingLicence.Worker

Consumes RabbitMQ messages and executes data validation, deterministic photo scoring, photo checks, risk assessment, automatic approval, failure, or manual-review routing.

DrivingLicence.Web

Optional Blazor interactive-server interface using Radzen controls. It creates multipart requests, polls status, displays history, and offers manual-review actions.

AppHost + ServiceDefaults

Aspire describes the local dependency graph. ServiceDefaults adds service discovery, HTTP resilience, health checks, structured telemetry, traces, runtime metrics, and OTLP export.

DrivingLicence.Tests

Unit, API, PostgreSQL, legacy-upgrade, and RabbitMQ end-to-end tests. Real dependency containers are created with Testcontainers.

Dependency direction

Web → API
API → Domain + Infrastructure
Worker → Domain + Infrastructure
Infrastructure → Domain

This preserves the most valuable Clean Architecture property: business rules remain independent of delivery and persistence frameworks, without introducing unnecessary repository or handler abstractions.

3. End-to-end processing flows

Submission and asynchronous processing

  1. The client sends personal fields and a face photo as multipart/form-data.
  2. The API validates the HTTP contract and optional Idempotency-Key.
  3. The photo is written to configured file storage; only its opaque path and metadata are stored in PostgreSQL.
  4. The API creates the application in Submitted, its first audit entry, and an outbox row in one database commit.
  5. The response is 202 Accepted; workflow execution is not performed inside the HTTP request.
  6. The outbox dispatcher publishes ApplicationSubmitted to RabbitMQ and marks the row published.
  7. The Worker consumes the message, performs checks, updates state, appends audit records, and stores the processed-message marker in one commit.

Manual review

  1. The reviewer reads an application whose state is PendingManualReview.
  2. The API verifies X-Reviewer-Key and checks the current state.
  3. Approve transitions to Approved; Reject transitions to Rejected and records the supplied reason.
  4. Any other starting state returns 409 Conflict; the aggregate also rejects illegal transitions.

5. Reliability and failure handling

Transactional outbox

Application, initial audit entry, and publication request commit together. A queue outage cannot lose the intent to process an accepted application.

At-least-once delivery

The same stable message ID may be published or delivered more than once. Correctness does not depend on exactly-once transport.

Idempotent consumer

processed_messages records consumed IDs. The marker and workflow updates use the same EF Core transaction, making redelivery a no-op.

Retries and error queue

MassTransit applies exponential retry. Exhausted deliveries are moved to the generated driving-licence-applications_error queue for inspection/replay.

Optimistic concurrency

PostgreSQL xmin prevents two reviewers or processes from silently overwriting the same application version.

Audit durability

Status changes go through the aggregate transition method, which validates legality and always creates a history entry.

Failure scenarios requested by the exercise

ScenarioBehavior
Same message processed twiceThe second delivery finds its processed-message ID and exits. The current-status guard provides a second defense.
API saves but queue publish failsThe unpublished outbox row remains durable and the dispatcher retries it on a later cycle.
Worker crashes before commitNo partial workflow update commits; RabbitMQ redelivers and the Worker retries.
Worker crashes after commit, before acknowledgementRabbitMQ may redeliver, but the committed processed marker makes it a no-op.
Business validation failsThe application transitions to Failed and the reason is persisted in audit history.
Unexpected infrastructure failureThe exception is logged, retried, and ultimately sent to the error queue; it is not misrepresented as a business rejection.

Photo choice: multipart avoids base64's approximate 33% size overhead. Local file storage is sufficient for the exercise. Production should use an injected object-storage implementation with signature validation, malware scanning, encryption, retention, signed access, and orphan cleanup.

Manual endpoints use a development API key to demonstrate an authorization boundary. Production should use OIDC/JWT authentication, reviewer roles, and include the authenticated reviewer identity in audit entries.

7. Operations and observability

  • Structured logs: JSON console logs include message IDs, application IDs, failures, and framework events.
  • OpenTelemetry: ASP.NET Core, outbound HTTP, runtime metrics, traces, and logs export through OTLP when configured.
  • Aspire dashboard: resource status, logs, traces, metrics, endpoints, PostgreSQL, and RabbitMQ management links.
  • Health: liveness /alive and readiness /health; API readiness includes PostgreSQL and MassTransit.
  • RabbitMQ management: inspect the main queue, _error queue, consumers, connections, bindings, and delivery rates.
Local versus production: Docker Compose uses HTTP for a zero-friction evaluator experience. Aspire supplies development HTTPS. Production TLS should terminate at managed ingress/reverse-proxy infrastructure.

9. Technical-review questions and answers

Why was this architecture chosen?
It isolates business rules, keeps HTTP work short, makes accepted submissions durable before queue delivery, and demonstrates realistic failure handling without over-engineering a small linear workflow.
How are invalid state transitions prevented?
The domain aggregate exposes TransitionTo, which checks a single allowed-transition map. Status setters are private. Manual endpoints additionally return a clear 409 before invoking the domain operation.
How are messages processed?
The API commits an outbox record. A dispatcher publishes its stable ID to RabbitMQ. A MassTransit Worker consumes it, loads the aggregate, executes checks, and commits state/history plus the processed marker.
Is the consumer idempotent?
Yes. It checks processed_messages by message ID, persists the marker in the same transaction as state changes, and ignores already advanced application states.
What happens when services crash?
API publication intent remains in PostgreSQL. Uncommitted Worker work rolls back and is redelivered. Committed work is protected from duplicate execution by the processed marker.
Why not use full Clean Architecture, CQRS, or a workflow engine?
The dependency direction is already domain-centric. Additional interfaces, generic repositories, commands, and framework machinery would provide little value for this bounded exercise. They become useful when use cases, integrations, teams, or workflow complexity grow.
What was AI-assisted?
AI assisted with scaffolding, implementation drafts, documentation, debugging, and test generation. Architecture and trade-offs were reviewed, the application was executed, and behavior was verified through unit and real-container integration tests.

10. Assumptions, shortcuts, and production improvements

  • Run reviewed migrations from a single deployment job instead of every application process.
  • Replace shared reviewer API keys with an identity provider, roles, and reviewer identity in the audit log.
  • Replace local photo files with object storage and add scanning, validation, encryption, lifecycle, and orphan cleanup.
  • Add outbox row leasing or FOR UPDATE SKIP LOCKED for efficient multi-replica dispatch.
  • Add rate limiting, secret management, PII redaction/encryption, retention/deletion policies, and security review.
  • Add alerting, dashboards, error-queue replay tooling, and deeper RabbitMQ readiness checks.
  • Expand tests for duplicate concurrent submissions, duplicate concurrent delivery, error-queue routing, and outbox recovery.
  • Split workflow stages into separate messages only when real external checks become slow and require independent retries or compensation.

Documented assumptions

  • Failed represents validation or technical-check failure; Rejected represents a manual business decision.
  • No automatic rejection rule was invented because the assignment specifies manual-review conditions and otherwise permits approval.
  • Malformed HTTP requests are rejected with 400 before application creation; valid submissions that fail workflow rules are persisted as Failed.
  • The UI is a bonus client; the API, Worker, database, queue, Compose setup, tests, and README remain the assignment's core deliverables.
